# 动量波段自动交易系统设计

Nov 24, 2026 · @ziqi

## 概览

这是一个确定性的规则引擎：在 IBKR 上按 Martin Luk 式动量波段规则自动筛选、下单和管理持仓。模拟盘和实盘共用同一套代码，只靠一个配置项切换。

**系统做的事**

- 盘前扫描候选股，算好均线、ADR 和关键价位
- 盘中识别入场形态，计算止损和仓位，提交括号单
- 收盘后更新跟踪止损，决定次日开盘要卖出的持仓
- 记录每一笔交易和每一次决策，供复盘

**系统不做的事**

- 不预测涨跌，不做主观判断
- 不交易期权、期货、杠杆 ETF
- 不做空（第一版关闭，后续可开）
- 不让 LLM 接触下单接口

**关键设计决定**

| 决定 | 选择 | 原因 |
| --- | --- | --- |
| 券商接口 | IBKR TWS API，经 IB Gateway | 模拟和实盘接口相同，只有端口和账户不同 |
| 核心回路 | 确定性代码，无 LLM | 可回测、可复现、不会算错仓位 |
| 止损位置 | 挂在券商服务器 | 程序掉线时仍有保护 |
| 账户状态 | 事件驱动加定时对账 | 比轮询及时，对账防漏消息 |
| 存储 | 本地 SQLite | 单机单账户足够，重启可恢复 |
| 语言和库 | Python 加 `ib_async` | 生态成熟，代码量最少 |

## 架构

&#91;embedded content: 系统架构 · 8 个模块，2 个环境\]

上面一排是下单路径，从左到右每一步都是确定性代码。券商的成交回报经事件与对账模块写回状态库，再供策略引擎下一轮使用。LLM 只能读状态库，只能给观察名单加标签。

| 模块 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| 调度器 | 按时间表触发各模块 | 交易日历、时钟 | 任务调用 |
| 行情与观察名单 | 拉取 K 线，算指标，筛选候选股 | 券商行情 | 当日观察名单 |
| 策略引擎 | 判定形态，算止损和数量 | K 线、账户状态、持仓、参数 | 交易计划或出场指令 |
| 风控闸门 | 逐项检查硬性限制 | 交易计划、账户状态 | 放行或拒绝，附原因 |
| 执行层 | 把计划变成订单并跟踪 | 放行的计划 | 括号单、改单、撤单 |
| Broker 适配层 | 封装券商接口 | 订单请求 | 券商回报、账户状态 |
| 事件与对账 | 处理成交推送，定时核对 | 券商事件 | 更新后的状态、报警 |
| 状态库 | 持久化一切需要跨重启保留的东西 | 各模块写入 | 查询结果 |
| LLM 旁路 | 主题标签、新闻摘要、复盘报告 | 状态库（只读）、新闻 | 文字和标签 |

## 模拟/实盘切换

模拟盘和实盘只差三样东西：端口、账户号、风控上限。策略代码读不到自己跑在哪个环境，所以在模拟盘跑通的逻辑到实盘不会变。

```yaml
mode: paper            # paper | live，唯一需要改的地方
profiles:
  paper:
    host: 127.0.0.1
    port: 4002         # IB Gateway 模拟盘默认端口
    account: DUxxxxxxx
    db: state_paper.db
    limits:
      risk_per_trade_pct: 0.5
      max_daily_loss_pct: 2.0
      max_positions: 5
      max_order_usd: 2000
  live:
    host: 127.0.0.1
    port: 4001         # IB Gateway 实盘默认端口
    account: Uxxxxxxx
    db: state_live.db
    limits:
      risk_per_trade_pct: 0.5
      max_daily_loss_pct: 1.5
      max_positions: 3
      max_order_usd: 400
```

两个环境用两个独立的数据库文件，避免模拟成交混进实盘记录。

**启动检查清单**

任何一项不通过，程序都退出或进入只读模式，不下单。

1. 读取 `mode`，加载对应的 profile
2. 连接 Gateway，取回当前登录的账户号
3. 账户号必须与配置完全一致。paper 模式下账户号必须以 DU 开头，live 模式下不得以 DU 开头。不能只凭端口号判断环境
4. live 模式额外要求环境变量 `TRADING_LIVE_CONFIRM` 等于实盘账户号
5. 确认能拿到实时的 5 分钟 K 线。拿到的是延迟行情时拒绝开新仓
6. 对账：券商的持仓和未成交订单与本地库逐项比对，不一致则只读并报警
7. 每个持仓都必须有对应的止损单在券商侧，缺失则立即补挂
8. 本机时钟与券商服务器时间偏差小于 2 秒
9. 全部通过后，在日志和报警通道里打印环境、账户号和当日风控上限

**模拟盘和实盘不一样的地方**

| 项目 | 模拟盘 | 实盘 |
| --- | --- | --- |
| 成交 | 模拟撮合，没有真实排队和滑点 | 突破单常成交在更差的价位 |
| 行情 | 默认延迟，需在账户设置里共享实盘订阅 | 按订阅的数据包 |
| 手续费 | 模拟计算 | 真实扣除，小账户占比高 |
| 心理压力 | 无 | 连亏时容易想手动干预 |

所以模拟盘验证的是程序有没有 bug，不能用来验证策略能赚多少。

## 券商适配层和下单流程

策略和风控只跟一个抽象接口打交道，换环境或换券商时只换实现。

```python
class Broker(Protocol):
    # 账户状态
    def account(self) -> AccountState: ...        # 净值、可用资金、当日盈亏
    def positions(self) -> list[Position]: ...
    def open_orders(self) -> list[Order]: ...
    # 行情
    def bars(self, symbol, timeframe, lookback) -> DataFrame: ...
    def subscribe_bars(self, symbol, timeframe, on_bar) -> None: ...
    # 下单
    def place_bracket(self, plan: TradePlan) -> BracketIds: ...
    def modify_stop(self, order_ref, new_stop) -> None: ...
    def close_position(self, symbol, qty) -> None: ...
    def cancel(self, order_ref) -> None: ...
    # 事件
    def on_fill(self, callback) -> None: ...
    def on_order_status(self, callback) -> None: ...
    def on_disconnect(self, callback) -> None: ...
```

| 实现 | 用途 |
| --- | --- |
| `IbkrBroker` | 模拟盘和实盘共用，只是连接参数不同 |
| `SimBroker` | 回测用，读历史 K 线并按设定的滑点和手续费模拟成交 |

**下单流程**

1. 策略引擎产出一份交易计划：代码、触发价、止损价、数量、3R 价位
2. 风控闸门逐项检查，任何一项不过就丢弃并记录原因
3. 计划写入本地库，状态 PENDING，生成唯一的订单引用号作为幂等键，防止重复提交
4. 拆成两组括号单提交：
   - A 组：计划数量的一部分，带止损单和 3R 限价止盈单
   - B 组：剩余数量，只带止损单，之后由程序按均线跟踪
   - 数量太少无法拆分时只下 B 组
5. 父单用买入止损限价单：触发价等于突破价，限价等于触发价加上允许的最大滑点。这样突破由券商服务器监控，程序不需要按秒轮询
6. 每组只有最后一张子单设置为立即传输，保证整组一起生效
7. 父单有效期为当日，收盘未触发自动作废

**事件处理**

| 事件 | 动作 |
| --- | --- |
| 父单成交 | 状态改为 OPEN，按实际成交价重算 R 和 3R 价位 |
| 父单部分成交 | 核对子单数量与已成交数量一致 |
| 止损单成交 | 状态改为 CLOSED，记录结果（R 倍数） |
| 3R 止盈成交 | 标记已分批，B 组继续持有 |
| 订单被拒 | 记录拒绝原因，不自动重试，报警 |
| 连接断开 | 自动重连；重连成功并完成全量对账之前禁止新单 |

IB Gateway 每天会强制重启一次，需要配置自动重新登录。重启期间止损单仍在券商服务器上有效。

## 策略引擎

策略引擎是一个纯函数：同样的 K 线、账户状态和参数，永远得到同样的动作。这使得任何一天都可以用历史数据重放并检查。

```python
def decide(bars, account, positions, params) -> list[Action]:
    ...
# Action 的种类：ENTER(plan) / EXIT(symbol, reason) / MODIFY_STOP(symbol, price) / NONE
# 每个 Action 带一个 reasons 列表，说明哪些条件满足、哪些不满足
```

**判定顺序**

1. 市场环境：QQQ 收盘在日线 EMA50 下方时，不产生 ENTER
2. 选股：只考虑当日观察名单里的股票
3. 形态 A，收紧后突破：近期出现内包日或极窄幅日，EMA9、21、50 靠拢，当日突破开盘区间高点
4. 形态 B，回踩均线：当日低点触及或刺穿前一日 EMA9 且不低于它超过 1 个 ADR，盘中重新站回并收在当日高位
5. 止损：开盘区间低点或当日低点。止损距离超过 ADR 的一半就放弃
6. 数量：账户净值 × 单笔风险 ÷ 每股风险，向下取整，再按单只仓位上限截断
7. 出场：收盘跌破 EMA9 的持仓，生成次日开盘卖出

**参数表**

来源一列说明这个数字是谁给的。标“默认”和“第三方复现”的需要在回测里校准。

| 参数 | 值 | 来源 |
| --- | --- | --- |
| 市场环境过滤 | QQQ 高于日线 EMA50 | 第三方复现 |
| 最低 ADR% | 4 | 默认 |
| 涨幅排名 | 1、3、6 个月涨幅各取前 2% 到 3% | 默认 |
| 最低日均成交额 | 2000 万美元 | 默认 |
| 开盘区间 | 前 5 分钟 | 默认 |
| 止损宽度上限 | ADR 的一半 | Martin Luk 本人 |
| 单笔风险 | 账户的 0.5%，上限 1% | Martin Luk 本人 |
| 单只仓位上限 | 大盘股 35%，中小盘 25% 到 30% | 访谈整理 |
| 分批止盈 | 3R 时卖出一部分 | 第三方复现 |
| 跟踪止损 | 收盘跌破日线 EMA9 | Martin Luk 本人 |
| 回踩入场确认时间 | 收盘前约 10 分钟 | 第三方回测 |

形态 B 里“盘中转强”还没有精确的量化定义，这是机械化版本和他本人主观判断差距最大的地方。

## 运行节奏

系统不需要按秒运行：最密的检查是每根 5 分钟 K 线一次，突破和止损都交给券商服务器上的挂单去盯。时间为美东时间。

| 时间 | 任务 | 频率 |
| --- | --- | --- |
| 08:30 | 启动检查和对账 | 一次 |
| 08:45 | 扫描候选股，算指标，查财报日历，生成当日观察名单 | 一次 |
| 09:25 | 提交昨晚生成的开盘卖出单 | 一次 |
| 09:30 到 09:35 | 记录每只观察股的开盘区间 | 一根 5 分钟 K 线 |
| 09:35 | 对符合形态 A 的股票挂出突破括号单 | 一次 |
| 09:35 到 15:45 | 检查回踩形态的前置条件 | 每根 5 分钟 K 线 |
| 15:50 | 对符合形态 B 的股票确认并入场 | 一次 |
| 16:05 | 更新日线和均线，找出收盘跌破 EMA9 的持仓，生成次日卖出清单 | 一次 |
| 16:15 | 生成当日复盘记录 | 一次 |
| 全天 | 订单成交、状态变化、持仓变化 | 券商主动推送 |
| 全天 | 券商状态与本地库对账 | 每 5 分钟 |
| 全天 | 连接心跳 | 每 30 秒 |

**账户状态什么时候读**

- 启动时读一次全量
- 每次下单前读一次净值和可用资金，用来算数量
- 成交事件到达时更新持仓
- 每 5 分钟对账一次，防止漏掉推送

运行时间只覆盖常规交易时段。盘前盘后不交易，美股休市日和半日市按交易日历跳过或提前收尾。

## 状态存储

持仓和订单以券商为准，本地库只负责记住券商不知道的东西：为什么进场、计划的止损在哪、已经分批了没有。

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `watchlist` | 每日观察名单 | date, symbol, theme, adr\_pct, ema9, ema21, ema50, earnings\_date |
| `decisions` | 每次判定的结果和理由 | ts, symbol, action, setup, reasons, inputs\_hash |
| `trades` | 一笔交易的完整生命周期 | id, symbol, setup, entry\_price, stop\_price, qty, risk\_usd, status, exit\_price, r\_multiple |
| `orders` | 发给券商的每张订单 | client\_ref, trade\_id, broker\_order\_id, role, type, qty, price, status |
| `fills` | 成交回报 | exec\_id, client\_ref, ts, qty, price, commission |
| `equity` | 每日净值快照 | date, net\_liq, realized\_pnl, peak\_net\_liq |
| `events` | 报警、断线、对账差异 | ts, level, kind, payload |

`decisions` 表里的 `inputs_hash` 是当次判定所用输入数据的指纹。用同样的数据重放，应该得到同样的结果，对不上就说明代码或数据有问题。

**重启恢复**

1. 从券商拉取持仓和未成交订单
2. 用订单引用号把它们和本地的 `trades`、`orders` 对上
3. 券商有而本地没有的持仓：标记为未知来源，只报警，不自动处理
4. 本地有而券商没有的持仓：查成交记录补全，按已平仓处理
5. 每个持仓确认有止损单，然后才恢复正常运行

## 风控

风控是独立于策略的一道闸门，策略无法绕过。所有限制写在代码和配置里，运行时不能被策略或 LLM 修改。

| 限制 | 模拟盘 | 实盘 | 触发后 |
| --- | --- | --- | --- |
| 单笔风险 | 净值的 0.5% | 净值的 0.5% | 按此计算数量 |
| 止损宽度 | 不超过 ADR 的一半 | 同左 | 放弃该笔 |
| 单只仓位 | 净值的 30% | 净值的 30% | 截断数量 |
| 同时持仓数 | 5 | 3 | 拒绝新单 |
| 单日亏损 | 净值的 2% | 净值的 1.5% | 当日停止开新仓 |
| 从净值高点回撤 | 15% | 10% | 停机，等人工恢复 |
| 单笔订单金额 | 2000 美元 | 400 美元 | 拒绝 |
| 每日下单次数 | 20 | 10 | 拒绝并报警 |
| 限价偏离最新价 | 超过 3% | 同左 | 拒绝 |
| 行情新鲜度 | 最新 K 线超过 2 分钟 | 同左 | 拒绝 |
| 财报窗口 | 财报前 2 个交易日内 | 同左 | 不开新仓；已有持仓在财报前一日收盘前平掉 |

表里的数值是起步用的默认值。每日下单次数这一条是为了防程序 bug 循环下单，不是策略需要。

财报窗口这一条来自财报日历，是确定性数据。持仓跨财报时股价可能跳空越过止损价，止损单会在远差于预期的价位成交，单笔亏损会超过设定的 0.5%。Martin Luk 本人如何处理财报没有找到明确说法，这条是保守的默认值。

**总开关**

- 工作目录下存在 `HALT` 文件时，停止开新仓，已有持仓和止损照常管理
- `flatten` 命令撤掉全部挂单并平掉全部持仓，只能由人手动执行
- 停机后的恢复必须由人删除 `HALT` 文件，程序不会自己恢复

**报警**

成交、拒单、断线超过 1 分钟、对账差异、触发任何一条停止类限制，都推送到手机。

## LLM 和新闻的位置

LLM 只放在下单路径之外：它的输出可以给观察名单加标签、写文字，但不能新增一笔交易，也不能改任何一个数字。LLM 不可用时系统照常运行。

| 环节 | 是否用 LLM | 说明 |
| --- | --- | --- |
| 形态识别 | 否 | 纯规则计算 |
| 止损和数量计算 | 否 | 公式，不允许近似 |
| 下单、改单、撤单 | 否 | 只由执行层调用 |
| 风控判定 | 否 | 写死的阈值 |
| 盘前主题归类 | 可选 | 给候选股打上板块或主题标签 |
| 新闻和催化剂摘要 | 可选 | 说明候选股近期为什么在涨 |
| 每日复盘报告 | 建议 | 读 `decisions` 和 `trades` 表写总结 |
| 异常日志解释 | 可选 | 把报错翻译成人话 |

**新闻面怎么用**

这套规则只看价格和成交量，核心回路不依赖新闻。新闻相关的数据分两类处理：

- **结构化的日程数据**，比如财报日期：直接进风控规则，见风控一节的财报窗口
- **非结构化的新闻文本**：只经 LLM 旁路变成标签和摘要，供人阅读和复盘

不让新闻情绪直接触发买卖，原因有两个：历史新闻的到达时间很难精确还原，回测不可靠；LLM 读错一条新闻就可能下错单。

如果以后要做财报或新闻跳空启动的形态（事件枢轴），触发条件仍然可以写成价格规则：跳空幅度、成交量倍数、是否站稳开盘区间。新闻只用来确认跳空有原因。

## 上线步骤

四个阶段依次进行，每个阶段有明确的通过条件，不满足就不进入下一阶段。

| 阶段 | 时长 | 验证什么 | 通过条件 |
| --- | --- | --- | --- |
| 1. 回测 | 写完即跑 | 规则实现是否正确；回撤和连亏有多深 | 同一天重放两次结果一致；计入手续费和滑点后期望值为正 |
| 2. 模拟盘 | 至少 4 周 | 程序稳定性 | 没有漏挂止损、没有重复下单、对账零差异；经历过至少一次断线重连和一次 Gateway 重启 |
| 3. 实盘最小仓位 | 至少 4 周 | 实盘成交与模拟的差距 | 每笔只买最小数量；统计出真实滑点和手续费，代回回测后期望值仍为正 |
| 4. 实盘正常仓位 | 持续 | 策略本身 | 每月复盘一次，累计 20 笔以上再评估胜率和盈亏比 |

从阶段 2 切到阶段 3 只需要改 `mode` 和设置确认用的环境变量，代码不动。

**退回条件**

- 实盘出现任何一次漏挂止损或重复下单：立即停机，退回模拟盘排查
- 触发回撤熔断：停机，复盘后由人决定是否继续
- 实盘滑点代回回测后期望值转负：停在最小仓位，不放大

## 假设和待确认事项

这份设计建立在几个还没核实的假设上，动手写代码前需要逐项确认。

- [ ] 账户类型：IBKR Canada 的现金账户、保证金账户还是 TFSA。TFSA 内频繁交易有被税务局认定为经营行为的风险
- [ ] 本金 1000 美元时单笔风险只有 5 美元，来回手续费占比很高。需要按实际费率重算期望值，或者决定先只跑模拟盘
- [ ] 目标股票能否通过 API 下碎股单。不能的话，高价股在小账户里无法按公式建仓
- [ ] 模拟账户的实时行情：确认已订阅数据包并共享给模拟账户
- [ ] 历史数据来源：回测需要几年的日线和 5 分钟线，并且要包含已退市的股票，否则结果偏乐观
- [ ] 财报日历的数据来源
- [ ] 参数表里标“默认”和“第三方复现”的项，用回测校准
- [ ] 形态 B 的“盘中转强”需要一个精确的量化定义
- [ ] 运行环境：本机还是云主机；Gateway 每日重启后的自动登录方式
- [ ] 报警推送用什么通道
